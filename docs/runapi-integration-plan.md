# RunAPI 独立采集接入方案

研究日期：2026-10-30（北京时间）。下文保留研究阶段所见198型号及设计依据；后续已完成正式接入并首次采集199型号，实施行为与运行结果以 [RunAPI采集运行说明](runapi-collection.md) 为准。未操作浏览器。

## 结论与当前规模

采用独立 `runapi_v1`，定价与监测两条任务，复用现有 SQLite、Worker、快照及卡片，不直接套用 PackyAPI 或 ZetaAPI 解析器。

| 项目 | 本次直接 GET 所见 |
| --- | --- |
| 定价型号 | 198 个不重复原始型号；166 个按量、32 个按次 |
| 公开定价分组 | 11 个，`usable_group` 与公开 `group_ratio` 对应 |
| 全部引用分组 | 15 个；另4个只在型号成员关系中出现，没有公开倍率 |
| 型号—分组关系 | 共390条，其中349条具有公开分组倍率、41条缺倍率 |
| 动态计费 | 8个型号返回 `billing_mode=tiered_expr` 和表达式 |
| 状态监测 | 8个 UUID 探测对象、7个不同型号；每对象60个带时间的点 |
| 状态周期 | 源返回7/15/30日成功数、总数及百分比；默认选中7日，应显式请求15日 |
| 原点时间跨度 | 60点在本次响应中约覆盖5小时15分钟，不是15日完整序列 |
| 更新频率 | `pollIntervalMs=300000`，即5分钟 |

本次 `runapi.host` 与 `runapi.co` 返回的型号集合一致；本机直连结果完整，`is_mainland_ip=false`、`mainland_display_policy_enabled=false`。这不证明阿里云服务器也会得到相同结果。

### 必须处理的四个问题

1. **地域展示策略**：公开公告提到新域名在部分访问环境只显示国内型号，前端也有地域过滤逻辑。不能把缩减目录直接当成模型下架。
2. **表达式优先**：`gpt-6.1-terra` 的普通倍率字段会导出75美元/百万输入Token，但表达式首档系数是0.4，且门槛是27,200。不能沿用普通倍率公式，更不能把门槛统一改成272,000。
3. **缺倍率分组**：`AWS稳`、`cc_sub`、`gemini-t3-1.5`、`gpt-image` 没有公开倍率。保留引用关系，不以1倍补值，不根据旧公告或显示文案猜价格。
4. **监测身份冲突**：`Codex - GPT-5.5` 在状态站报错，但当前定价目录的 `gpt-5.5` 只属于 `default/Plus`。这条旧Codex探测应保留原始历史并标记映射冲突，不混入当前Codex分组，也不转给其他组。

**分层结论：**

- **公共业务API**：定价JSON和站点公开配置，正式采集主源。
- **公开页面数据接口**：状态站 `/api/dashboard`，同样可以服务端直接GET，不需要自动化浏览器。
- **页面/资源补充**：Logo、文档、公开前端的计费展示规则。资源文件名含hash，必须从入口发现，不能将本次文件名长期硬编码。
- 登录后的充值报价、消费日志、账户/管理接口不在采集链路内；不发模型推理请求，不消耗用户余额。

## 2. 目录与价格规范

### 全量与完整性保护

- 原始型号名为主键，不用显示名、厂商翻译或标签拼身份。厂商先按 `vendor_id` 关联；少数源厂商名有乱码，原值保留，展示归一化另存。
- 以原始 `enable_groups` 保存全部390条关系；以公开倍率和可用分组定义生成349条可计算报价。4个引用组另标 `referenced_only / ratio_unpublished`，不假造价格，也不将41条关系丢掉。
- 前端继续只展示适合公开报价的分组；引用组不是凭空增加的可购买卡片。198个型号仍完整保存，不因其另有缺倍率成员关系而丢弃型号。
- 每轮记录源域名、型号集合hash、厂商/平台分布、分组数量、成员数、可计算报价数、缺倍率数量及地域策略。
- 后续若总量低于上份有效目录80%，或Claude/GPT/Gemini等既有平台整族消失，拒绝破坏性覆盖，安排补采并保留last-good。80%是初始保护阈值，不是永久固定198个型号。
- 在服务端按采集器专用出口配置访问公共来源，不用伪造身份头替代真实网络差异。两域来源必须使用同一轮对应配置，不能混拼不同地区/时点的目录和倍率。

### 三类价格分别计算

| 类型 | 处理 |
| --- | --- |
| 普通按量 | 输入=`model_ratio × 2 × group_ratio`；输出再乘 `completion_ratio`，单位为站内美元额度/百万Token |
| 缓存 | 缓存读乘 `cache_ratio`，写乘 `create_cache_ratio`；零值与未提供区分，不通过truthy默认值填1 |
| 按次 | `model_price × group_ratio`，源定价页按次展示；不统一改成每秒/每张 |
| 动态表达式 | `billing_expr` 高于普通倍率字段，解析各档输入/输出/缓存和条件，不再额外乘普通倍率的2倍系数 |

本轮8个表达式型号：`gpt-6.1-terra`、`gpt-6-astra`、`gpt-5.6-luna`、`deepseek-v4.1-flash-1017`、`gpt-6.1-sol`、`gpt-5.6-terra`、`gpt-5.6-sol`、`gpt-6-sol`。

- 实现受限语法解析，支持本次出现的变量、算术/比较/逻辑/三元运算及 `tier/hour/weekday`，不对外站表达式使用 `eval` 或 `Function`。
- 保留表达式原文、hash、解析版本、档位名称、变量系数、条件阈值及源时区。未知语法仅隔离对应型号的数值报价，原型号和原始表达式仍保存，不能退回明显错误的普通倍率价。
- DeepSeek的表达式包含北京时间工作日9–12点、14–18点的双倍条件。存基准和高峰规则；现价导出时求值，并令快照有效期不越过下一次价格边界。不能等6小时后才更新界面现价。
- 明确区分当前价、档位范围和基准价，不能用最低档冒充所有请求价。存储精度不裁为两位，显示继续走现有价格格式化组件。

### 币种、充值和折扣

公开配置当前为：`quota_display_type=USD`、`quota_per_unit=500000`、`price=6.75`、`usd_exchange_rate=7`、`stripe_unit_price=8`。前端人民币参考价采用 `美元额度价 × price`。

- 原始报价币种记录为**站内美元额度**，不是人民币1:1额度，也不是已验证的实际付款金额。
- 基础充值配置、展示汇率、Stripe支付单价分字段、分来源保存。若展示充值信息，用“公开配置参考”口径，不合成统一实时成交汇率，不叠加已过期的充值促销。
- `GroupDisplayRatio` 中的“0.73折/倍率0.5”等是分组说明文案，当前和结构化倍率存在不一致。作为源声明保存，但不覆盖定价JSON，不给每个型号套同一折扣。
- 型号折扣优先使用明确的型号级同币种同单位数据；本次没有独立型号折扣字段，则使用我们的官方参考目录计算。同型号、同计费档位、同单位才能比较；现金价和美元额度价不可混用。无可比基准就不显示折扣。
- 记录 `discount_source / reference_source / currency_basis / tier / observed_at`；比较缓存读价、图片按次价或视频价时不与文本输入Token混算。

### 图片、视频与其他模态

- 本次标签包含21个图片、12个视频型号，也有音频、音乐、embedding、rerank。按标签、协议和型号证据联合分类，不能只看 `quota_type`。
- Gemini部分生图型号是按Token计费，应保存输入/图片输出的真实收费，不强行按张；GPT-Image当前接口为按次，不用旧公告覆盖现状。
- 视频文档给出时长/分辨率等调用参数，但当前定价JSON只给基础按次价，未提供完整价格变体表。没有源定价规则时只展示“基础单价/次”，不自行换算为每秒、默认8秒套餐或官方估算范围，不加约等号。
- 图片和视频继续沿用现有专用价格列表，文本Tab不混入图片/视频。文档参数可入元数据，不作为已验证的额外收费表。

### 探测身份不能按标题随意合并

8个探测对象均有UUID、明确的 `model`，但本次 `latest.groupName` 全部为null；6个 `groupInfos` 是页面分类信息，不能当成定价站分组主键。

| --- | --- | --- | --- |
| Claude_lite - Claude-Opus-4-8 | claude-opus-4-8 | claude_lite | 标题前缀、原始型号、当前成员关系三项校验 |
| Claude_normal - Claude-Opus-4-8 | claude-opus-4-8 | claude_normal | 同上；不是把lite组的数值复制过来 |
| Claude_normal - Claude-Sonnet-5 | claude-sonnet-5 | claude_normal | 同上 |
| Codex - GPT-5.5 | gpt-5.5 | codex | 当前成员关系冲突，暂停绑定，原探测仍入库 |
| Codex - GPT-5.6 | gpt-5.6-sol | codex | 使用 `model` 而非标题里的GPT-5.6生成身份 |
| Default - DeepSeek-v4-pro | deepseek-v4-pro | default | 校验型号成员关系后绑定 |
| Default - Gemini-3.1-Pro | gemini-3.1-pro-preview | default | 不能据页面分类名绑定到discounts组 |

- UUID身份、标题、原始model、端点或组归属发生变化时生成绑定版本并记录原因，不将旧数据静默重解释成另一个型号/组。
- 不根据“官方渠道相同”说明给coding组复制claude_normal的直接探测。
- `officialStatus` 是上游OpenAI/Anthropic等服务状态，单独保存，不能当RunAPI成功率。
- 完整错误文本只作排查证据，现有浮层只显示时段、可用率、耗时和覆盖等简洁信息。

### 已提供与未提供的性能字段

| 字段 | 口径 |
| --- | --- |
| status | 正常、延迟、失败、验证失败、维护、错误六类，保留原状态 |
| latencyMs | 对话响应/探测耗时；不是TTFT |
| pingLatencyMs | 网络探测耗时；不从对话耗时中相减来制造TTFT |
| checkedAt | 原始探测时间，归一到UTC并保留原精度用于去重 |
| 15d totalChecks/operationalCount/availabilityPct | 官方15日探测正常率汇总，独立保存 |
| TTFT、TPS、缓存命中率 | 本次接口均未提供，保持null，不显示0、不推算 |

源页面明确说明 `degraded` 是“响应成功但耗时升高”。因此需要分别保存“正常达标”和“响应成功”两种计数：

- 本站正常可用率采用正常探测数/有效探测数；延迟降级单独计数，不叫作无差别请求成功率。
- 对话平均耗时包含 `operational + degraded` 的有效正耗时，避免把慢但成功的请求全删掉导致虚假低延迟。
- 失败、错误、验证失败不混入成功响应耗时。维护表示停止检查，单独记录，不补成功；未知状态隔离，不默认映射成功。
- 源15日汇总按原值和原始分子分母保存，不假设维护/降级在源统计中与本地公式完全一致。

## 4. 十五日保存与统一聚合

### 汇总与原点严格分开

`trendPeriod=15d` 能拿到15日百分比和计数，**不能拿到15日每小时历史**。本次7日/15日请求中的时间线仍然都是每对象60点。

- 最近60点增量入库，`latest` 与 `items` 中相同记录只计一次。当前响应为480个唯一探测点，不是488个。
- 原点持续积累，保留至少35日。按UTC小时构建有效探测数、正常数、降级数、失败数和耗时合计，生成滚动360小时。
- 本站主百分比与60根6小时细条采用同一份保存历史、同一小时网格；缺小时仍是灰条，不把官方15日总数摊进360个桶。
- 官方15日摘要从首轮就保存，在现有可用率浮层以“站方15日摘要”独立展示；不得拿它充当我们还未积累到的15日耗时。后续若将其改作主值，必须同时明确与细条覆盖范围不同，不能无标记切换口径。

### 整站、模型、分组

- 整站：每小时先对同型号多个有效探测对象等权，再对型号等权，最后对有记录小时等权；重复测Opus不会让该型号翻倍占权。
- 型号：只取精确 `model` 匹配的有效对象，绝不拿Claude Opus填Claude Opus 5.5，也不以平台均值补尚未监测的最新型号。
- 分组：有校验过的组内探测就聚合该组被监测型号，明确这是抽样探测，不是该组全量请求SLA。
- 没有组级记录时，复用 `withModelDerivedGroups`，仅以当前组实际成员中有历史的型号生成“系统汇总”；没有任何型号记录的组保持空态，不套整站值。
- `samples` 为小时覆盖并集，`probeCount` 为探测数量，二者分开；可用率0%的真实失败数据仍必须保留。
- RunAPI时间行使用现有“最近耗时 / 15日均”，不把 `latencyMs` 贴上“首Token”；缺TPS继续保留现有空值语义，不增占位装饰组件。

## 5. 入库结构和保留期

继续使用 `transit.sqlite` 和原子写入的 `data/transit/latest.json`，不建立第二份独立快照或让前台直接访问状态站。

| 表/结构 | 处理 |
| --- | --- |
| transit_stations/groups/offers | 现有主表；记录站点、真实分组、公开报价和引用但缺倍率的分组状态 |
| transit_quote_observations | 保存价格历史，不用二位小数展示值反写原价 |
| transit_source_snapshots | 所有公开响应的源URL、时间、schema、hash、原始文件位置、解析结果 |
| 建议新增 transit_runapi_catalog_versions | 保存整个目录版本、公开可见性、198型号原字段、390成员关系、倍率/字段缺口和地域审计 |
| 建议新增 transit_runapi_billing_versions | 按型号、源版本及解析版本保存表达式、档位、时间规则、币种基础；金额/系数使用精确十进制文本 |
| 建议新增 transit_runapi_probe_targets | UUID身份、精确model、原groupName、标题前缀候选、绑定版本、匹配/冲突状态、首次/末次出现 |
| 建议新增 transit_runapi_probe_observations | 主键站点+UUID+源checkedAt；原状态、两类耗时、源model/绑定版本、原始hash、首次/末次采集时间 |
| 建议新增 transit_runapi_probe_hourly | 主键站点+UUID+UTC小时；各状态数量、正常率、成功耗时和/数量、首末点、最大缺口、当前小时partial |
| 建议新增 transit_runapi_monitor_summaries | 主键站点+UUID+7/15/30日+源生成时间；源分子分母、百分比和采集时间 |
| 建议新增 transit_runapi_metadata_observations | 基础充值配置、显示汇率、分组说明、公告、Logo指纹；支付方式及促销有效期分开 |
| 现有采集run/schedule表 | 复用独立报价/性能任务、lease、fail_count、next_collect_at和last_error |

不直接复用Zeta的探测表：Zeta对象是整数ID的心跳，RunAPI是UUID的对话/内容验证探测，状态及耗时语义不同。

- 相同探测重复回扫只更新last_seen，不增加计数；相同源时间出现冲突载荷时保留审计记录，不静默覆盖历史。
- 原点、小时桶和滚动摘要至少35日；报价版本/绑定审计长期保留；原始响应文件按hash去重，至少保留7日并保护last-good引用，有界清理。
- 目录、分组、报价在一笔事务中提交；原始快照失败/冲突记录单独可追溯；性能失败不回滚有效定价，定价失败不清空有效探测。
- 前台只读取预聚合结果。逐小时中间序列不放入公开JSON，继续只输出60根条及必要覆盖元数据。

## 6. 自动采集和失败恢复

| 任务 | 初始安排 |
| --- | --- |
| 型号/价格/分组 | 每6小时全量2个业务JSON请求，失败独立退避 |
| 公开状态 | 每5分钟一次dashboard请求，显式 `trendPeriod=15d`；同一响应已含7/15/30日摘要，无须分三次请求 |
| 绑定复核 | 每次价格目录或状态对象变化时自动重核 |
| 时段价格边界 | 已存表达式在写侧/快照过期判断中本地求值，不为每个价变节点重新请求远端 |
| Logo与文档 | 初始化、资源变更或每日低频复核；不重复下载近7MB主脚本作为日常采集步骤 |
| 保留期清理 | 成功采集后有界执行，不删除仍被引用的有效证据 |

- 沿用 `pnpm worker` 每分钟检查任务，再启动独立单站子进程；不新增cron，不因重启丢掉入库历史或既有下一次执行时间。
- 单站报价与性能分别租约，禁止同站重复占用。状态API按5分钟节奏拉取，不轮询每个型号的推理端点。
- 条件请求支持属于实施项：在共享传输层新增显式可选的ETag/304处理并回归默认行为；未启用前使用内容hash去重。当前共享fetch不能直接把304当成功使用。
- 20秒请求超时、响应体上限、有限重定向和明确域名白名单；每轮串行、有限请求，不对404分组接口反复重试。
- 403/429停止当轮并遵循Retry-After；网络失败指数退避；入口200但schema/完整性异常同样记失败。
- 监测和定价跨域网络分别诊断。部署后先在服务器运行同样的公开GET核对完整性；必要时使用现有按站点出口配置，不硬编码IP或关闭证书校验。
