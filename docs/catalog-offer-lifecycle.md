# 商品下架与旧报价处理（首批）

## 已实现

- ShopApi 类目失败返回失败；分页异常或到达分页上限标为非完整结果。
- 完整成功的缺失商品标 pending；空成功同样处理。部分成功只更新看见的商品，不据此判下架。
- 商品 status 明确禁用标 delisted；Worker 对完整列表中缺失的商品最多复核3条，单条10秒超时，串行300ms间隔；仅同源商品详情接口。网络/认证/WAF问题仍为 pending。
- 明确未上架/已下架/不存在/已删除时，保留历史 tombstone，不从数据库/快照硬删除。原始缓存不能覆盖已有 tombstone；下一次真实列表重新出现可以恢复 active。
- 前台隐藏 delisted 和超过24小时未见的记录；pending 不参与最低价/有货数。active 报价在24小时公开窗口内继续显示**上次确认的库存**，最近采集成功的渠道参与汇总；超过2小时只加现有“待更新”提示，不把正常库存改成“待核验”或缺货。最近采集失败的渠道保留上次库存及“待更新”说明，但不参与当前最低价/有货/缺货统计，其分组按待核验处理，失败不等于售空。
- 汇总区分“有货 / 无货 / 待核验 / 暂无报价”；只有确认的库存为空才显示无货。某质保分组有缺失待核验渠道时，不因没有最低价就断言全部售空；无该分组报价显示暂无报价。
- 非ShopApi 采集器未声明完整性时保守合并，不根据缺失撤展。

## 2026-11-07 链动库存排查

实测截图两件商品：goodsList 的 `extend.stock_count` 分别为38、40；原采集器输出与线上页面传入的报价均为 `status=in_stock`、`lifecycle=active`，库存完整保存。线上报价最后成功看到时间为当天17:41，读取时已超过两小时。原展示函数把“两小时未更新”当成“不再有货”，导致库存数字被隐藏、价格划线及有货数归零；不是库存字段丢失。

当前按**库存事实、商品生命周期、更新时效**分别处理，24小时边界仍保留，不延长公开展示窗口，不修改旧报价时间，也不通过重分类伪造新的采价记录。仅更新前台代码并重建就能恢复窗口内已保存的正确库存；无需离线把 pending 强制改成 active。

同时实测公开 goodsInfo：商品可上架且 `status=1`，但 `extend` 不含库存。该接口成功只能说明详情可访问，不能证明有货；缺失列表商品仍需下一次真实列表确认，详情请求不得刷新 `lastSeenAt` 或复活库存。新增回归从真实形态的38/40件样本走采集、raw保存、public/latest写入、商品搜索及最低价汇总，并验证失败保留、零库存、低库存、明确下架与两小时/24小时边界；测试使用临时目录，不改真实库存文件。

## 运行与剩余工作

新增逻辑由常驻 pnpm worker 执行，不由页面请求触发。首次部署后按店铺下一轮采集逐步收敛，单店缺失较多时跨轮次检查，按最后复核时间轮换。

本批未修改线上数据，未全量扫描旧报价。仅主Worker启用详情复核；手工 collect:shopapi 会传递采集完整性，缺失项先置待核验，详情核验由Worker后续处理。
