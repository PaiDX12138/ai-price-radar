# RunAPI 采集运行说明

RunAPI已通过独立 `runapi_v1` 采集器接入，不复用Packy或Zeta的采集解析器。页面沿用现有站点卡、分组价格区、模型监测区与统一浮层，没有增加新的布局或配色。

## 更新与初始化

```bash
pnpm transit:migrate
pnpm collect:transit -- --station=runapi
pnpm transit:status
```

部署后持续采集由既有 `pnpm worker` 完成。Worker每分钟发现 `config/transit/*.json`，独立运行 `--due --station=runapi`；不新增cron。只启动 `pnpm start` 不会持续采集。

| 任务 | 默认频率 | 来源 |
| --- | --- | --- |
| 全量报价和公开元数据 | 6小时 | `https://runapi.host/api/pricing`、`/api/status`；显式备选域名 `runapi.co` |
| 状态/耗时/摘要 | 5分钟 | `https://status.runapi.co/api/dashboard?trendPeriod=15d` |
| 时段报价 | 本地重算 | 已保存的受限DSL；每分钟快照导出和页面服务端视图均重算，无额外网络请求 |

报价与性能分别持久保存租约、成功/失败时间、下次执行时间及退避。一次站点actor原子认领任务，另一个进程无法强制抢占有效租约。重启不会重置历史；一次性能失败不阻止有效价格发布。

## 目录与价格

- 核对全量型号、主要平台和上一有效数量；地域限制、整族缺失或大幅缩水拒绝清空last-good。两个API域名有明确白名单，同轮定价与元数据配对读取。
- `usable_group`和公开倍率定义可报价组。缺倍率的引用分组保存但不展示虚构报价；完整成员关系独立存表，绝不以1倍补价。
- 普通按量：输入`model_ratio × 2 × group_ratio`，输出再乘completion；缓存0值与未提供区分。
- `tiered_expr`优先于普通倍率，受限语法解析并以十进制文本计算收费系数。不执行源JS，不使用eval；非线性/未知表达式仅隔离对应型号报价，保留原型号和表达式审计。
- 8个已观察动态型号有输入阈值或北京时间工作日高峰规则。`gpt-6.1-terra`阈值27,200，与其他型号272,000不混。报价浮层沿用已有完整报价组件展示档位，不重排模型行。
- 所有表达式价格含本组倍率一次；DeepSeek高峰只在本地求值，不以6小时旧价格冒充当前价。读侧仅运行本地受限解析器，不打开数据库或请求外站。
- 按次单价以“次”为单位；图片按Token型号保留Token口径，不能将视频基础价换成每秒。目录、原始字段、表达式/倍率保持精度，展示用既有格式化。
- 币种为站内美元额度，现有标签显示“USD额度”；基础充值、显示汇率和Stripe配置在同一浮层区分，未使用已过期充值活动或把额度当实际付款金额。
- 折扣采用现有参考目录的同型号/同单位基础输入比较，明确标注美元额度面值，不包含充值差价。动态多档价或无可比参考的型号不伪造折扣；分组宣传文案单独保存，不能覆盖型号计算。

## 性能口径

- 按UUID保存真实探测，原始 `model` 为型号身份，标题里的简写不能替代原始model。
- 本次源 `groupName` 为null；用标题组前缀、公开组键、当前型号成员关系交叉匹配，保存 `matched / membership_conflict / unmapped` 状态与绑定版本。
- 同一型号的两个有效对象先等权，再对型号和小时等权。每次快照导出再次检查当前成员，价格更新后旧映射不能继续混入。
- 当前8个对象中7个匹配、1个Codex GPT-5.5成员冲突，冲突记录仍保存，但不混入整站/型号/分组聚合；有效覆盖6个型号，不声称全目录均被监测。
- `operational`是正常达标；`degraded`响应成功但耗时升高，另计数且计入成功耗时；失败/验证失败/错误不混入成功耗时。维护保留原点，但不作为成功或失败分母。
- `latencyMs`为对话响应耗时，`pingLatencyMs`独立保存，不能减出TTFT。源没有TTFT/TPS/缓存命中率，继续显示缺失语义。
- 首页/分组时间行使用现有“最近耗时 / 15日均”。每对象最近60点增量累积，源7/15/30日摘要分开保存；15日摘要不铺成360个小时。
- 主可用率和60根6小时细条使用本站同一360小时历史，无记录时段灰色、不补成功；源15日汇总在既有浮层独立显示。
- 有有效组内探测的组优先；没有时按真实成员调用共享分组汇总，标“系统汇总”。组内无任何型号历史继续为空，不借用整站数据。

## SQLite与归档

复用 `transit.sqlite`、报价主表/报价观察、run/schedule、源快照登记及原子写 `data/transit/latest.json`，新增8张专用表：

| 表 | 保存内容 |
| --- | --- |
| transit_runapi_catalog_versions | 全目录JSON、完整性计数、来源和版本hash，数组顺序变化不制造新语义版本 |
| transit_runapi_memberships | 全部型号—分组关系、公开价格是否可得、active状态 |
| transit_runapi_billing_versions | 原始表达式、parser版本、解析错误、型号版本hash |
| transit_runapi_metadata_observations | 公共配置、分组宣传文案、公告和充值配置，不含登录态 |
| transit_runapi_probe_targets | UUID、型号、候选组、绑定版本、映射状态及源对象 |
| transit_runapi_probe_observations | 唯一站点+UUID+UTC微秒时间；原状态、响应/Ping耗时、指纹、源hash、first/last_seen |
| transit_runapi_probe_hourly | 各状态计数、成功耗时和/数量、首末点、缺口及partial |
| transit_runapi_monitor_summaries | 源7/15/30日分子、分母、百分比和生成时间，独立于小时数据 |

相同探测重扫不增加样本，载荷冲突回滚该批并记失败。源归档为内容hash命名的gzip JSON，数据库只保存索引，不重复写整段dashboard正文。以本次数据为例约170KB响应压缩为约12KB；摘要仅3种窗口，不发3遍请求。原点/小时/摘要至少保留35日；原始响应至少7日、有界清理，并保护各来源最新证据和last-good引用。价格/绑定审计长期保留。

未监测型号复用前台既有空态，不在快照里为每个型号重复输出60根空桶；目录与报价仍完整保存，实际有探测的型号才输出模型时序。

## 网络与故障

单请求20秒、单站180秒预算，串行且有限请求，响应体限制4MB。403/429立即停止当前定价域名尝试并遵循Retry-After，性能是独立状态源和独立退避。404分组接口不再请求。

沿用 `TRANSIT_RUNAPI_HTTP_PROXY` 或既有全局出口配置；设置`direct`才显式直连。不写死IP、不关闭TLS校验、不伪造IP身份头。网络/schema/完整性失败均保留原价和已有小时历史。

本版使用内容hash去重，没有更改共享fetch的304语义，也不会为同步远端数据访问管理、账户、充值下单或模型推理接口。
